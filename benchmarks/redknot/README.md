# RedKnot benchmarks on DeepInfer

This directory migrates the reproducible RAG workloads from **RedKnot-SGLang** to a framework-independent, sealed input manifest and a **native DeepInfer full-recompute baseline**. The first native model is DeepSeek-V4.1-Flash-1017. Other model configurations are retained with explicit support status.

The native runner measures requests through `LLMEngine.add_request`, `step`, and the final asynchronous output flush. It does not substitute an HTTP server or Transformers inference for DeepInfer. This change does not implement RedKnot's optimized attention/KV reuse path, and it does not publish a GPU speedup.

## Freeze inputs with the target tokenizer

Use Python 3.12+ and the target model's Transformers/tokenizers environment. Only `prepare` needs those CPU dependencies; `catalog`, `validate`, `summarize`, and `compare` use the standard library. All commands below run from the repository root. Tokenizer/checkpoint paths must be local. Custom tokenizer Python requires explicit `--trust-remote-code`.

```bash
python -m benchmarks.redknot catalog

python -m benchmarks.redknot prepare \
  --suite 64k --model-profile deepseek-v4.1-flash \
  --tokenizer /path/to/DeepSeek-V4.1-Flash-1017 \
  --output benchmark-output/v41-64k.manifest.json

python -m benchmarks.redknot validate benchmark-output/v41-64k.manifest.json
```

Preparation preserves source query rows, evidence chunk positions, and complete question-context text. It rebuilds chunks with the selected target tokenizer, trims distractors when necessary, and deterministically adds dataset rows to fill the document budget. It fails if a complete evidence context cannot fit its chunk. The final V4.1 single-user, text-only **chat** prompt follows the official encoding format, then is encoded once with special tokens explicitly present. Other profiles require their tokenizer's own chat template.

The manifest records target token IDs, per-case token hashes, answer hashes, source selections, evidence retention, chunk transformations, tokenizer asset hashes, and a whole-manifest seal. Runtime consumes those IDs directly. It never treats the old V4-0731 token IDs/hashes as V4.1 inputs. The length label is a **document budget**: chat framing, query instructions, and BPE boundaries change the final request length, which is recorded as `input_tokens`.

One held-out warmup question is generated by default; its query row and final input hash differ from measured cases. Background documents can overlap. Warmup is excluded from measured latency and QA. `--warmup-count` controls the number of warmup requests.

To include all five datasets using a new selection of two short-answer questions per dataset:

```bash
python -m benchmarks.redknot prepare \
  --suite 64k --model-profile deepseek-v4.1-flash \
  --tokenizer /path/to/DeepSeek-V4.1-Flash-1017 \
  --datasets hotpotqa 2wikimqa musique multifieldqa_en triviaqa \
  --cases-per-dataset 2 \
  --output benchmark-output/v41-five-datasets.manifest.json
```

For a smaller admission smoke test, use `--max-cases 1` and keep the native context budget, or explicitly set `--target-tokens` to a smaller budget that still contains the evidence. A subset or changed budget is recorded and must not be reported as the full release suite. `--max-new-tokens` changes short-answer limits; the original long showcases retain their fixed output budgets.

## Run the native baseline

Install the selected DeepInfer runtime and its submodules according to [the repository instructions](../../README.md). The launcher supports **one Linux node with NVIDIA GPUs**. The checked-in upstream runtime targets SM100; H200/SM90 execution requires a separately installed compatible port. `--runtime-root /path/to/that/DeepInfer` explicitly selects that checkout and records its commit, dirty-source hashes, and submodule state. Selecting a checkout is not hardware qualification. Multi-node and Ascend launch/aggregation are not implemented in this harness.

```bash
python -m benchmarks.redknot run \
  --manifest benchmark-output/v41-64k.manifest.json \
  --model-path /path/to/DeepSeek-V4.1-Flash-1017 \
  --ep 8 --cp 1 --warmup-iterations 3 --iterations 10 \
  --output-dir benchmark-output/v41-64k-baseline

python -m benchmarks.redknot summarize \
  benchmark-output/v41-64k-baseline/report.json \
  --manifest benchmark-output/v41-64k.manifest.json
```

By default DP size is `max(ep // cp, 1)`. **Each DP rank runs the entire cohort**, rather than sharding a single copy of its cases. Thus EP=8, CP=1 gives 8 DP ranks; a 15-case suite with 10 measured iterations has 1,200 measured request observations and 15 unique cases. The report separates these counts. The launcher requires a contiguous numeric GPU block and validates device availability. It fixes greedy sampling and a deterministic per-case seed, disables speculative decoding and expert rearrangement, and records effective runtime settings.

For long-context cohorts, add `--admission-batch-size 1` to admit and fully drain one request at a time on each rank. Larger explicit values use fixed batches in manifest order. Every rank still executes every case; this does not shard the cohort. The same bound applies to warmup, and `max_num_seqs` is capped by the largest actual batch. Omitting this option preserves the original whole-cohort admission behavior. `--max-num-batched-tokens` only bounds prefill work per engine step; it is not a limit on the KV memory of all active requests. Sequential admission reduces concurrent state demand but does not guarantee that a single long request fits the selected runtime's memory.

An explicit admission batch size is part of comparison metadata. Reports record each batch's index, ordered sample IDs and per-rank duration, and each request names its batch. Each iteration's global elapsed time is **the sum of the slowest rank's time in each batch**, not the maximum of the ranks' total times. Request TTFT begins at that request's admission; it excludes previous batches. Input preparation, inter-batch synchronization, progress logging and output decoding remain outside these execution windows. Consequently, batch sizes define different scheduling workloads and cannot be mixed in a paired comparison. Old reports without batch metadata remain valid under their original timing contract.

For a broader functional run, use `--admission-batch-size 1 --warmup-iterations 3 --iterations 3 --timeout-seconds 21600`. The deadline covers startup and all warmup/measured work; it defaults to 7,200 seconds. Every completed batch writes a flushed `redknot_batch_complete` JSON event to each rank log with phase, iteration, batch index, sample IDs and local elapsed time. A timed-out or failed run still produces failure diagnostics instead of a partial success report. The shell wrapper accepts and forwards both new options.

`--batch-invariant 0` explicitly selects kernels without batch-invariant mode when required by a qualified SM90 port (default: `1`). Port-specific environment settings such as `DEEPINFER_ENFORCE_EAGER=1`, `DEEPINFER_DFLASH_ENFORCE_EAGER=1`, `DEEPINFER_PREFILL_ATTEMPT_INTERVAL=1`, and `DEEPINFER_PREFILL_ANY_ATTEMPT_INTERVAL=1` must be set before starting the runner; they are captured in its launch and report. Use the port's complete dependency environment and validated settings. An external runtime alone does not supply those dependencies.

For a shared GPU host with a lifecycle supervisor, use `--supervised-process-group` only under that supervisor. All rank descendants then remain in its process group, and it owns final descendant cleanup and resource restoration. The runner still terminates its direct ranks on failure. In this mode, the exact `REDKNOT_GLM_RUN_ID` key is recognized as a lifecycle ownership marker, not an optimized-kernel setting; other active RedKnot overrides remain rejected. Standalone launches use the runner's own rank process groups by default.

Each phase starts after rank synchronization and CPU input conversion. TTFT runs from native request admission to the first token observed by the engine API; latency ends at the observed final token. Phase duration includes queueing, execution, and final draining. Global phase duration is the slowest DP rank's duration; global throughput divides all completed requests by the sum of these synchronized phase durations. Token decoding and disk output occur outside this timing window. This is **not the original SGLang HTTP streaming TTFT boundary**, so their published speedups cannot be carried over.

Dedicated warmup requests do not prove every measured input shape has already been compiled. Runtime compilation inside a measured phase is included in its native latency. Inspect logs and qualify compilation-cache steadiness before treating a run as stable performance, particularly when comparing different implementations. The manifest and matching metadata checks alone do not establish that qualification.

Output includes the frozen manifest, launch settings, rank logs, rank request records, and the sealed `report.json`. A failed rank stops this launch's other worker processes and produces failure diagnostics instead of a success report. Existing output directories and manifest files are never overwritten. `--warmup-iterations 0` is an explicitly cold smoke run and is ineligible for comparison.

The report also records benchmark Python file hashes and the loaded native engine module/extension file hashes, verifying the latter agree across DP ranks. Source identity alone does not identify compiled artifacts; this record covers the observed engine modules, not every dynamically compiled GPU kernel.

To prepare and run all four suites sequentially:

```bash
bash scripts/run_redknot_benchmarks.sh \
  --model-path /path/to/DeepSeek-V4.1-Flash-1017 \
  --output-root benchmark-output/v41-release
```

Add `--prepare-only` for CPU preparation, `--suites "64k 128k"` for selected lengths, or `--runtime-root` for an explicitly installed alternative backend. Set `PYTHON_BIN` if the environment uses a different interpreter.

## Scores and comparable reports

Short answers use English normalized exact match and token F1, independently maximized across accepted references, reported on a 0–1 scale. Long fixed-output showcases do not contribute to QA scores. The report includes per-dataset aggregates, unique cases, repeated observations, native TTFT/latency p50 and p95, and observed throughput. Percentiles use Hyndman–Fan type 7 interpolation.

`summarize` revalidates the full cohort against its manifest. `compare` additionally requires matching model/tokenizer identities, runtime/settings/hardware, warmup, timing boundary, and every expected `(iteration, dp_rank, sample_id)`. Missing/duplicate samples, failed requests, invalid durations, mismatched token inputs, or incomplete fixed-length outputs are rejected. Controlled fixed-output QPS speedup is available only when the entire cohort is fixed-output; natural-EOS and mixed workloads retain observed throughput without that speedup claim.

```bash
# Requires a future real RedKnot native implementation that emits the same report contract.
python -m benchmarks.redknot compare \
  --manifest benchmark-output/v41-64k.manifest.json \
  --baseline benchmark-output/v41-64k-baseline/report.json \
  --redknot /path/to/verified-redknot/report.json \
  --output benchmark-output/comparison.json
```

There is currently no `run --mode redknot`. A RedKnot report must attest activation and name its implementation/configuration; changing a baseline label is rejected. That attestation is a software contract, not independent evidence of correct kernels or measured acceleration. Checkpoint configuration, tokenizer assets, weight index hashes, weight file sizes/mtimes, and runtime source identity are recorded; full multi-hundred-GB weight content hashing is explicitly not performed.

## Validation and remaining work

```bash
python -m unittest discover -s tests/redknot -v
python -m ruff check benchmarks tests/redknot
python -m ruff format --check benchmarks tests/redknot
bash -n scripts/run_redknot_benchmarks.sh
```

CPU tests cover source-integrity failures, evidence retention and deterministic selection, target input seals, async output flushing and admission failures, rank aggregation, strict report compatibility, and QA metrics. Fake engines test the measurement contract; they do not establish GPU kernel correctness or performance. Full-suite native GPU qualification, optimized RedKnot execution, additional model backends, and multi-node qualification remain separate validation milestones.

The [2026-10-28 CPU tokenizer validation record](validation/v41-tokenizer-cpu.json) checks the actual V4.1 tokenizer against all 60 release cases plus a 10-case matrix covering all five datasets, with five additional warmup cases. Every evidence context was retained and every input ID fits the checkpoint vocabulary. Rebuilding the 64K manifest produced the identical seal. Final release request lengths were 65,579–65,640 / 131,113–131,176 / 262,193–262,251 / 450,610–450,656 tokens. This record contains no model output, QA score, or GPU timing. Whole-manifest hashes include local tokenizer paths; portable per-case token hashes and tokenizer fingerprints are recorded separately.

The [2026-10-28 native SM90 smoke record](validation/v41-sm90-native-smoke.json) validates the complete execution path using an external, modified PR148 runtime. One 65,585-token HotpotQA question ran on each of eight DP ranks, after a separate warmup request. All eight measured requests completed with natural EOS and the expected answer, `Miller v. California`; report/cohort checks passed and the lifecycle supervisor restored the GPU holder. This is **one unique question**, not an eight-question accuracy evaluation. The record includes raw native timing observations for audit, but one warmup and one measured iteration do not qualify stable performance or acceleration.

Hardware values have distinct sources: the sealed smoke record's `nvidia-smi`/NVML inventory reports **NVIDIA L20X, compute capability 8.9**. A separate read-only query on 2026-10-28 using the qualified environment's CUDA 13.2 compatibility Driver API (`libcuda.so.595.45.04`, `cuDeviceGetAttribute`) reports **NVIDIA L20X, compute capability 9.0** on all eight devices. That query created no CUDA context or inference workload. The reason for this capability discrepancy has not been confirmed; the host's H200 connection alias does not independently establish its GPU product identity. The historical JSON retains the original inventory values.

The successful smoke's external runtime records 34 modified or untracked source/test files beyond PR148 base commit `731508b4282cee87f526a492c6bad8cabcc2f35c`. Those exact local file versions and the installed dependency/build environment are not provided as a complete reproduction package in this branch. Published source and binary hashes identify the observed runtime; they do not reconstruct its missing patches or build artifacts. This smoke therefore does not establish that a clean clone of the public SM100 checkout can reproduce the SM90 run.

An [independent reproduction check](validation/v41-reproduction-check.json) exported clean benchmark sources from `18936fe` and rebuilt all 60 release inputs, 10 five-dataset matrix inputs, and five warmup inputs with the real V4.1 tokenizer. All five complete manifest seals and every measured input-token hash matched the published CPU record. These are input configurations, not 75 independent questions.

The same check then started a fresh native process using the existing external runtime and repeated the exact 64K smoke. Both sealed baseline reports passed cohort validation. All recorded metadata, runtime source/binary hashes, and all eight ranks' output token IDs, answer text, finish reason, and EM/F1 matched. The measured question was still a single HotpotQA example. The lifecycle supervisor exited successfully and restored the holder; post-run source and binary fingerprints remained unchanged.
